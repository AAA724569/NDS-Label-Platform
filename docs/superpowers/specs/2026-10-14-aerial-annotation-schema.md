# 两表标注存储设计

用户已在本对话批准精简方案，并明确要求执行新建。

## 范围

新增且只新增 `aerial.annotation_batches` 与 `aerial.annotation_batch_videos` 两张表。
已有 `aerial.videos` 是视频来源，保持其结构和数据不变；一个采集文件夹对应一块电池批次。
批次表合并代表帧、补帧 JSONB、模型原文、标签 JSONB、模型/提示词/格式版本和审核信息。
关联表通过 BYTEA SHA256 外键连接视频，一个视频属于一个批次。

## 数据约束

批次 UUID；内部文件夹唯一且非空；代表帧的源视频、毫秒时间戳及图片位置必须完整提供或全为空。
代表帧源视频必须属于该批次，使用可延迟的复合外键支持先建立批次再建立视频关系。
标签与补帧均为 JSONB 数组；ROI 为 JSONB 对象；模型原始输出为 TEXT，以保存不合法 JSON 的响应。
审核状态为 pending/approved/rejected。批准需要已通过格式校验、非空标签、完整代表帧和审核人/时间。
标签或证据改变会递增修订号并回到待审核，保留原始模型输出与当前整理结果，不建立完整历史表。
完整标签字典、补帧成员检查、视频内时间上限由后续写入接口校验；本次仅建立存储。

## 权限与统计

新对象应由 aerial schema 的现有所有者维护。`reader` 获得两张新表 SELECT，不获得写权限。
不创建新的管理员、写入账号，不改数据库认证规则。
视频数/时长由关联的有效 `videos` 行计算；帧动态标签只支持帧观察，不能扩为整个批次出现时长。
内部表含路径、SHA256、审核人及原始响应；公开统计站后续通过字段白名单获取审核结果。
仅创建表不自动生成批次、不调用模型、不接入当前页面，也不自动同步 Metabase 元数据。

## 实施和验证

迁移在单一事务执行，遇已有同名表则失败回滚，避免接受未知结构。
使用独立 PostgreSQL 14 实例验证约束、reader 权限、修订更新和重复迁移回滚。
维护连接可用后执行真实迁移，用 reader 核对新表可读/不可写及既有视频行数。
